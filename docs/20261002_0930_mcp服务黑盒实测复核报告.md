## 1. 测试范围与方法

### 1.1 环境前提（重要）

本机设置了 `http_proxy/https_proxy` 指向 `127.0.0.1:10808`（hiddify）。**未经 `--noproxy` 的 curl 请求会返回 502 Bad Gateway**，与被测服务无关。后续所有客户端配置需确保 localhost 不走代理，否则会误判服务不可用。

### 1.2 探测维度

| 维度 | 用例数 | 方法 |
|---|---|---|
| 鉴权 | 11 | 无 key / 错 key / 空 key / Bearer / 小写 bearer / Basic / 尾随空格 / query string / 大小写变换 / GET 健康检查 |
| Origin 与 CORS | 11 | 7 种 Origin（含 `null`、`file://`、`http://127.0.0.1.evil.com`）+ 预检 + 非预期方法 |
| 协议一致性 | 28 | 版本协商、未知方法、resources/prompts/logging、批量、坏 body、id 类型、Content-Type |
| 参数校验 | 18 | 类型错误、非法枚举、未知字段、越界值、缺失必填 |
| 分页边界 | 15 | limit 0/1/5/50/100/101/500/1000/10000/-1/2³¹ + 5 种 cursor |
| 过滤语义 | 26 | 用**正确参数名**逐维度验证 |
| 写路径 | 30 | 建/改/删/提案/幂等/批量/dryRun + 11 组非法写入 |
| 并发 | 6 | 1/4/8/16/32/64 并发 |
| 批量与畸形 | 16 | 6 项批量混入非法项、10 种畸形 body、1MB 垃圾体 |

### 1.3 一次重要的自我纠错

首轮过滤测试我使用了 `status`、`priority`、`keyword`、`startDate`、`projectId`、`tagId` 等参数名，**全部返回 225 条全量数据**，初看像过滤器整体失效。复核 schema 后发现正确命名是 `statuses`/`priorities`/`searchQuery`/`dateScope`/`projectIds`/`tagIds`——是我的测试错了，不是服务错了。

但这次误测反而暴露了一个真实且严重的问题：**服务对完全未知的参数名也是静默忽略而非报错**（见 §5.1）。如果模型也猜错名字，后果与我的首轮测试完全相同：拿到未过滤的全量数据并据此汇报。参数名设计不够直观，加上零校验，共同构成了 P0。

### 2.3 唯一架构隐患

`query_tasks` 每次调用都执行 `context.repository.exportAll()` 全量导出，再在内存中过滤（`query_tasks_tool.dart:123, 216`）。实测延迟随 `limit` 增长而非随库大小增长，说明 225 条时导出成本可忽略。

**但这是 O(全库) 的操作。** 数据量到几万条时，每次查询都要拉全表、构建 4 个索引结构（`projectsById`、`taskTagIdsMap`、`tagsById`、`childrenIndex`），延迟会线性劣化。225 条无感，5 万条会是另一个故事。

同文件注释自述"directly from memory cache"，但实现走的是 `exportAll()`。若未来数据量增长，这是**第一个需要改的地方**。

### 3.1 做得好的部分

| 项 | 实测结果 |
|---|---|
| 监听地址 | `127.0.0.1:8765`，非 `0.0.0.0`（`ss -ltnp` 确认） |
| 外部 Origin 拦截 | `http://evil.com`、`https://evil.com`、`http://127.0.0.1.evil.com`、`null`、`file://` **全部 403** |
| DNS rebinding 防护 | `127.0.0.1.evil.com` 被正确识别为非本地并拒绝 |
| 本地 Origin 放行 | `http://localhost:3000`、`http://127.0.0.1:9999`、`http://[::1]` 正常 200 |
| 双通道 key | `x-api-key` 与 `Authorization: Bearer` 均支持，且大小写不敏感 |
| 方法限制 | `PUT` / `DELETE` 返回 405 |
| 预检 | `OPTIONS` 返回 204 |
| Body 读取超时 | 10s 上限，防挂死 socket |
| 坏 body 处理 | 坏 JSON → -32700；空 body / 非对象非数组 → -32600 |

### 3.2 问题

| # | 问题 | 证据 |
|---|---|---|
| S1 | **GET 健康检查不鉴权**即吐 `toolsCount`、`authRequired`、`endpoint` | 无 key 请求返回完整状态 JSON。本地场景风险低，但顺手加 key 更好 |

## 4. 协议一致性

### 4.1 当前实现

- `protocolVersion`：`2024-11-05`，硬编码于 `mcp_server.dart:27`
- 支持方法：`initialize`、`notifications/initialized`、`ping`、`tools/list`、`tools/call`
- 不支持：`resources/*`、`prompts/*`、`logging/*`、`completion/*`（均返回 -32601，客户端可容忍）
- 传输：无状态 HTTP POST + JSON-RPC，无 SSE / Streamable HTTP session
- `initialize` 只声明 `{tools:{listChanged:false}}`

### 4.2 协议问题清单

| # | 问题 | 实测 | 影响 |
|---|---|---|---|
| P1 | **协议版本硬编码，不协商** | 客户端要 `2025-06-18` / `2025-03-26` / 乱码，一律回 `2024-11-05` | 永久放弃 2025-03-26 的 `structuredContent`、`annotations`、tool `title`。返回旧版本本身合法，但应 echo 客户端版本 |
| P2 | **无 tool annotations** | `ai_tool.dart:123-129` 仅输出 `{name, description, inputSchema}`。全仓库零 `readOnlyHint` / `destructiveHint` / `idempotentHint` / `openWorldHint` | **见 §6.2，这是最高影响项** |
| P3 | 空 batch 返回 `[]` + 200 | — | JSON-RPC 2.0 要求全通知 batch 返回单个错误对象 |
| P4 | 通知类 POST 返回 204 | 实测 `notifications/initialized` → 204 | 2025-03-26 Streamable HTTP 规定 **202 Accepted** |
| P5 | `params['name']` 非字符串 → -32603 | 实测 `{"name":123}` → `Internal error ... type 'int' is not a subtype of type 'String'` | 应为 -32602 Invalid params |
| P6 | 批量非法项静默丢弃 | 6 项 batch 只回 3 条，`42` 和 `"str"` 无任何错误响应 | 违反 JSON-RPC 规范；客户端无法察觉请求被部分忽略 |
| P7 | 无 `structuredContent` / `outputSchema` | 全部结果为 `content[0].text` 的 JSON 字符串 | 模型须重新解析，易臆造字段名，且浪费 token（见 §8） |
| P8 | `initialize` 少报 capability | — | 客户端探测 `-32601` 后忽略，属机会缺失而非破坏 |
| P9 | `jsonrpc` 字段不校验 | `jsonrpc:"9.9"` 甚至缺失都正常响应 | 宽松，不致命 |

## 5. P0 缺陷：静默错误数据

> 本节所有问题共同特征：**服务不报错，模型不知道自己做错了什么，然后基于错误数据给出自信的答案。** 这比崩溃危险得多。

### 5.1 未知参数名静默忽略（实测确认）

schema 无 `additionalProperties: false`，实现对未声明键直接忽略。

| 实测输入 | 正确参数名 | 返回 |
|---|---|---|
| `{"status":"todo"}` | `statuses` | **225 条（全量）** |
| `{"keyword":"应用"}` | `searchQuery` | **225 条（全量）** |
| `{"startDate":"2026-10-01"}` | `dateScope` | **225 条（全量）** |

模型猜错参数名 → 拿到**未过滤的全量数据并据此汇报"你有 225 个待办"**，而用户以为在看筛选结果。

### 5.2 非法枚举静默退化为"不过滤"

| 实测输入 | 返回 |
|---|---|
| `{"statuses":["bogus"]}` | 225 条（全量） |
| `{"dateScope":"bogus"}` | 225 条（全量） |

`query_tasks_tool.dart:126-135` 的 `for` 循环匹配不到就落回 `DateScopeEnum.all`，无 `else` 分支。

**且 schema 本身有缺口**：`dateScope` 的 enum 漏了 `customRange`（`DateScopeEnum` 有、引擎也实现了），而 `completedScope` 的 enum **列了** `customRange`。模型按后者的经验去试前者 → 静默变成查全部。

### 5.3 `statuses` 的默认值描述是假的

`query_tasks_tool.dart:72-73` 声称：

> Default is `["todo", "inProgress"]` if asking for pending tasks, or `["done"]` for completed tasks.

**代码里没有任何默认值。** `:137-148` 留下空数组，而 `matchesFilter` 把空数组当**无过滤**。

实测算术印证：baseline = 225，`statuses:["todo"]` = 112，`statuses:["done"]` = 113，**112 + 113 = 225**。即默认返回**全部任务，含已完成**。

后果：模型问"我今天有什么"，`query_tasks({dateScope:"today"})` 会把今天已完成的、已取消的一起返回。schema 里也没有 JSON-Schema `default` 可供模型锚定。

### 5.4 日期解析失败返回 null 而非报错

`ai_date_parser.dart:13-40` 无法解析时返回 `null`。`create_tasks_tool.dart:157-173` 拿到 null 就当"没传日期"，正常创建。

**实测全部返回 `status:"created"`：**

| 输入 | 实际结果 |
|---|---|
| `"not-a-date"` | 创建成功，**无日期** |
| `"tomorrow"` | 创建成功，**无日期**（未支持相对日期） |
| `"下周一"` | 创建成功，**无日期** |
| `"2026-02-30"` | 创建成功，**无日期**（非法日期未校验） |

模型汇报"已安排到下周一"，任务实际没有日期。**数据完整性缺陷伪装成成功。**

schema 只声明支持 ISO 8601 和 `yyyy-MM-dd HH:mm`，但未说明"解析失败会静默忽略"。仓库里已有自然语言快速录入解析器（`quick_capture_bar.dart`）具备相对日期能力，只是未接入。

### 5.5 bulk dryRun 几乎不校验，且从不校验日期

`create_tasks_bulk_tool.dart:109-157` 的 dryRun **只校验标题非空 + 项目存在**。

结合 §5.4：**一批 `dueDate` 全部无效的任务，dryRun 会报 `valid:true`，然后创建 100 个无日期任务。** dryRun 在最需要它的场景下给了假保证。

其他实测：
- 150 条超限 → 正确报错 `BATCH_LIMIT_EXCEEDED`（含 `count` / `limit` details），这是好的错误设计
- 部分失败 → 正确逐项报告 `{total:2, succeeded:1, failed:1}`，非原子性已在 description 中诚实声明

### 5.6 写入校验几乎不存在

| 实测输入 | 返回 | 实际行为 |
|---|---|---|
| `priority: 9` | `ok: true` | 静默 clamp |
| `priority: -1` | `ok: true` | 静默 clamp |
| `priority: "high"` | `TOOL_EXECUTION_EXCEPTION` | **泄漏 Dart 堆栈**（见 §5.7） |
| `status: "bogus"` | `ok: true` | 静默忽略 |
| `status: 99` | `ok: true` | 静默忽略 |
| `priority: 42` | `ok: true` | 静默 clamp |
| `update_task` 无任何字段 | `ok: true` | **静默 no-op** |
| `update_task title: ""` | `ok: true` | 静默忽略 |

### 5.7 类型错误泄漏内部堆栈

`ai_tool_registry.dart:82-87` 的 catch 把完整 Dart 堆栈塞进 message：

```
Failed to execute tool "query_tasks": type 'String' is not a subtype of type 'num?' in type cast
#0      QueryTasksTool.execute (package:ordo/c...
```

暴露内部包路径，且对模型完全无用。应转为 `INVALID_ARGUMENT` 并说明正确取值。

### 5.8 错误信息中英混杂

| 错误 | 语言 | 错误码 |
|---|---|---|
| `"Task title cannot be empty."` | 英文 | `INVALID_ARGUMENT` ✅ |
| `"有子任务的任务状态由子任务派生，不可手动修改"` | **中文** | `REPOSITORY_ERROR` |
| `"任务标题长度需在 1–200 字符之间"` | **中文** | `REPOSITORY_ERROR` |
| `"截止时间不能早于开始时间"` | **中文** | `REPOSITORY_ERROR` |

`REPOSITORY_ERROR` 还泄漏了"这是仓储层错误"这一实现细节。模型看到中文错误时，若自身推理链是英文，处理质量会下降。

## 6. P0 缺陷：写路径无护栏

### 6.1 默认直写 + 客户端可越权

**实测默认模式是 `direct` 直写**：`create_tasks` 不带 `mode` 直接落库，`requiresConfirmation: false`。

更关键的是 `mode` **客户端可覆盖**（`create_tasks_tool.dart:144-146`，`create_tasks_bulk_tool.dart:104-106`、`update_task_tool.dart:163-165`、`delete_tasks_tool.dart:64-66` 相同）：

```dart
final isDirect = requestedMode == 'direct' ||
    (requestedMode != 'proposal' && context.writeMode == 'direct');
```

用户开启「提案审核队列」后，**任何客户端、任何注入进客户端的 prompt 都能传 `mode:"direct"` 直写 SQLite**。服务端策略是建议性的，不是强制的。

**建议**：从所有 schema 移除 `mode`，或把客户端 `direct` 开关做成默认关闭的显式配置。

### 6.2 缺 annotations → AI 删任务树零提示（最高影响）

`ai_tool.dart:123-129` 不输出任何 `annotations`。后果双向：

**危险侧**：`delete_tasks` 是**硬删 + 级联**，`docs/40-data-model.md:197` 确认，且 tombstone 只存 `(type, id, updatedAt)`——**标题不可恢复**。而 **Claude Code / Claude Desktop 正是靠 `destructiveHint` 决定是否弹窗确认**。当前状态是 AI 删掉一整棵任务树，用户零提示，不可撤销。

**烦扰侧**：5 个只读工具也没有 `readOnlyHint: true`，读一次弹一次确认。

**这是全清单性价比最高的一项：约 15 行。**

### 6.3 `idempotencyKey` 在 direct 模式下根本没实现

schema 明确承诺（`create_tasks_tool.dart:68-72`）："Optional client token to prevent duplicate task creations on retries."

**实测：同一 key 连续两次调用 → 两个不同 taskId。**

原因：`create_tasks_tool.dart:185` 才读 key，而 direct 分支 `:182` 已经 return 了。`update_task_tool.dart:69-72` vs `:202`、`delete_tasks_tool.dart:30-33` vs `:95` 同样问题。幂等仅在 `proposal_repository.dart:108-115` 的提案路径生效。

**默认模式下重试即产生重复数据**，而 schema 让模型以为不会。

### 6.4 其他写路径缺口

| 缺口 | 位置 | 影响 |
|---|---|---|
| `dryRun` 只有 bulk 有 | `create_tasks_bulk_tool.dart:62-66` | `create_tasks` / `update_task` / `delete_tasks` 均无预检 |
| `update_task` 无 before/after diff | `update_task_tool.dart:175-190` | 模型无法自检"X→Y 改对了么" |
| `delete_tasks` 无预检、无标题解析、无存在性校验 | `delete_tasks_tool.dart:68-92` | 模型幻觉出一个 ID 就硬删 |
| `create_tasks` 不能设 `notes` / `parentId` | `create_tasks_tool.dart:21-75` | 子任务仅限 `substeps`（扁平 1 层，无日期无优先级）；无法把已有任务挂到父任务下 |
| `update_task` 不能改 `parentId` / `sortOrder` | `update_task_tool.dart:21-75` | **重组任务树和手动排序完全不可能** |

## 7. P1 问题：模型看不见你的组织方式

### 7.1 folders 和 customViews 被加载后直接丢弃

`todo_repository.dart:1230-1249` 的 `exportAll()` **已经返回** `folders` 和 `customViews`，而 `query_tasks_tool.dart:123` 拿到后**直接扔掉**。这是本节所有问题的根源。

| 缺失能力 | 数据已在 | 后果 |
|---|---|---|
| **Folders** | `export.folders` | 不可列举。`get_metadata` 只回 `folderId` 不回名字，模型拿到不透明 UUID，无法回答"工作下的所有事" |
| **Custom views** | `export.customViews` | **不暴露**。而 customView 的 panel filter 本质是**用户亲手写好的 `FilterCriteria` 预设**（`custom_view_models.dart:227-265`）——这是给 NL→查询编译器最便宜的 grounding 素材，白扔 |
| 过滤引擎能力 | `custom_view_models.dart:41-50` | `folderIds`、`tagMatchAll`、`hierarchyScope`、`customDateStart/End` 均已实现，schema 全无 |
| 排序能力 | `custom_view_models.dart:691-731` | `sortBy`/`sortDirection` 已实现未暴露。**任何稳定分页的前置条件** |
| 树形查询 | `task_query_engine.dart:48-94` `filterTree` | 用的是 `filterFlat`，搜子任务会返回**孤儿行**（`parentId` 指向模型没见过的父任务，`:308`） |

### 7.2 无项目/标签管理工具

`get_metadata` 只能读。AI 无法创建、重命名、删除项目或标签。

连带损失：`projectName` 已在 `create_tasks` 返回中给出，模型完全有能力按名字建项目（`get_task` 返回了 `projectName`，但 `create_tasks` 的 schema 描述写的是"Target project ID"）。

**这就是本次测试无法清理副作用的原因（见 §10）。**

### 7.3 `get_metadata` 不报 `writeMode`

实测返回 keys 恰好是 `['now', 'projects', 'tags']`。模型每次写完都得解析响应体才知道自己写进库还是写进队列。**一个字段就能省掉每次写入的一次往返。**

### 7.4 输出形状自相矛盾

实测对比：

| 概念 | `query_tasks` | `get_task` | 写入入参 |
|---|---|---|---|
| 截止时间 | `dueDate`（格式化字符串） | `dueAt`（裸 epoch ms） | `dueDate` |
| 开始时间 | `startDate` | `startAt` | `startDate` |
| 完成时间 | `completedDate` + `completedAt` | `completedAt` | — |
| 优先级 | `"high"`（字符串） | `"high"` | `3`（整数 enum） |
| 标签 | `["mcptest"]`（字符串数组） | `[{id,name,color}]` | — |

同一字段三种表示法，且跨工具不一致。模型每次都要做心智翻译。

**其他缺口：**
- `query_tasks` 输出**不含 `notes`**，而 `searchQuery` **匹配 notes**（`custom_view_models.dart:504-510`）——搜到了却读不到为什么命中
- `query_tasks` 输出不含 `updatedAt`、`sortOrder`
- `get_task` 声称返回 "full subtask hierarchy"，实际调 `getDirectChildren`（`get_task_tool.dart:50-53`），深度 3 的树被静默截断为 1 层
- `get_task` 返回**原始 `task.status`**，而 `query_tasks` 计算 `derivedStatus`（`:241-243`）。子任务全完成的父任务，`get_task` 读作 `todo`，`query_tasks` 读作 `done`
- `get_metadata` 的 weekday 硬编码中文（实测 `星期五`）。`AiToolContext.locale` 默认 `'zh'`（`ai_tool.dart:11`）且 `mcp_server_provider.dart:83-88` **从未赋值** —— 英文 UI 也回中文
- `get_metadata` **无时区**：`now.iso` 是本地时间无偏移量，模型无法判断"今天"的边界

### 7.5 `aggregate_tasks` 无时间维度

`aggregate_tasks_tool.dart:18-37` 只有 `groupBy` / `projectId` / `status`。

**"我这周完成了多少"——最常见的个人分析问题——无法回答。** 而 `completedAt` 字段早在迁移 v7 就存在（`40-data-model.md:223`），完全闲置。

实测：`aggregate_tasks({groupBy:"project"})` 仅 890 字符就把全局统计说清楚了——**这个"省 token"的设计思路是对的，应该推广到所有工具。**

## 8. Token 成本分析

性能不是瓶颈，**上下文才是**。

| 项目 | 字节 | 估算 tokens | 说明 |
|---|---|---|---|
| `tools/list` schema | 10,142 | ≈3,169 | **每次会话常驻**，11 个工具 |
| `get_metadata` | 2,003 | ≈625 | |
| `query_tasks` limit=5 | 1,845 | ≈576 | |
| `query_tasks` limit=30（默认） | ~11,000 | ≈3,400 | |
| `query_tasks` limit=50 | 19,720 | ≈6,162 | |
| `query_tasks` limit=200 | **74,344** | **≈23,232** | **一次吃掉大半个上下文** |
| `aggregate_tasks` by project | 890 | ≈278 | 最省的调用 |

**问题：**

1. `tools/list` 3.2k tokens 常驻。11 个工具里 `create_tasks` / `update_task` / `create_tasks_bulk` 三个的 schema 高度重叠（`title`/`description`/`priority`/`startDate`/`dueDate`/`projectId`/`tags`/`substeps`/`mode`/`idempotencyKey` 几乎全同），是明显的合并空间。
2. `limit` 无 schema `default` / `maximum`，只有 description 里一句"default: 30, max: 200"。模型不知道边界在哪，容易直接请求 200。
3. `limit` clamp 静默发生在 `query_tasks_tool.dart:172-173`：传 0 或负数→返回 1 条；传 10000→返回 200 条。模型不知道自己被截断了。
4. 无 `structuredContent` / `outputSchema`（§4.2 P7），模型须重新解析 JSON 字符串，白白消耗 token 且易臆造字段名。

## 9. 改造优先级清单

> **总体原则：第 1–6 项都是 XS/S，合起来把"AI 会误用的工具面"变成"AI 能安全使用的工具面"。后面所有有想象力的功能都建立在"模型读到的可信、写入的含义明确"之上——先修护栏，再修功能。**

### 第一梯队：护栏（必须先做）

| # | 项目 | 影响 | 工作量 | 风险 | 说明 |
|---|---|---|---|---|---|
| 1 | 加 tool `annotations`（`ai_tool.dart:123-129`）；5 个只读工具 `readOnlyHint:true`，`delete_tasks` 加 `destructiveHint:true` | **高** | XS | 无 | 约 15 行。Claude 停止自动删除任务树。纯安全收益 |
| 2 | 移除客户端 `mode` 越权；`get_metadata` 与所有写响应回显 `writeMode` | **高** | XS | 低（用户会察觉行为变化） | 提案队列目前保护不了任何东西 |
| 3 | `AiDateParser` 改为失败即报错（`UNPARSEABLE_DATE` + `details:{raw, expectedFormats}`），并支持相对日期（tomorrow / 下周一 / in 3 days / EOD / 本周末） | **高** | S | 低 | 消除"静默无日期任务" |
| 4 | `query_tasks` v2：真实 `sortBy`/`sortDirection`（复用 `sortPanelTasks`）、不透明 cursor、schema 补 `default`/`maximum`、暴露 `folderIds`/`tagMatchAll`/`hierarchyScope`/`customRange`、`includeAncestors`→`filterTree`、输出补 `notes`/`updatedAt`、**修掉撒谎的 `statuses` 默认值** | **高** | S | 低 | 后续所有功能的前置条件 |
| 5 | 严格参数校验：`additionalProperties:false` + 未知字段报错 + 非法枚举报错（而非退化为不过滤） | **高** | S | 低（会暴露既有的错误调用） | 直接消除 §5.1 / §5.2 |
| 6 | `idempotencyKey` 在 direct 模式真正生效（`task_proposals` 式去重表，或内存 LRU 存 24h） | **高** | S | 低 | schema 已承诺，当前是谎言 |

### 明确不建议做

- **不要建 SSE / Streamable HTTP。** 当前无状态 HTTP POST 对本地单用户服务器是合法且够用的设计。修完 annotations、mode、协议版本协商即可停止。
- **不要保留路径不校验的行为作为"待修项"。** 它意外兼容了不同客户端的路径约定，应在文档中明确说明并保留。

## 附：一句话总结

**传输层是合格的，性能是充裕的，但安全契约是破损的。** 当前状态下，AI 可以：拿到未过滤的数据却以为已过滤、把任务创建成无日期却汇报"已安排"、静默忽略非法参数、绕过人工审核直写数据库、以及在用户零提示的情况下不可逆地删除整棵任务树。

修复清单里最值得先做的三件事，加起来不到一天：**加 annotations（15 行）、把 `mode` 越权关掉、让日期解析失败时报错。**
