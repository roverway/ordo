## 一、 背景与设计目标

### 1.1 背景
应用近期接入了 AI Copilot 功能，具备基于自然语言的任务解析与创建能力。但早期实现主要依赖单一的 Prompt 文本补全与一次性 JSON 提取，存在以下局限：
1. **数据单向且隔绝**：AI 无法自主查询已有的待办事项、项目分类和标签词典，在处理模糊指代（如“把今天未完成的任务列出来”、“修改昨天的周报会议时间”）时容易产生信息幻觉。
2. **缺乏统一通信标准**：应用内部缺少一套标准的工具调用机制与规则定义，无法让 AI 根据用户意图灵活决策并调度合适的接口。
3. **避免重复造轮子**：应用在之前的迭代中已经构建了高性能的统一多维查询引擎（`TaskQueryEngine`，Commit `835d5642a85dd0267d883bb8c50edccb3a100994`），具备完整的任务过滤与筛选逻辑，必须充分共用，避免两套查询逻辑产生不一致。
4. **保留未来开放 MCP 能力**：需要同时支持应用内直接的工具调用（Tool Calling），并保持架构对 Model Context Protocol（MCP）标准的完全兼容，使后续对外开放接口时无需重写底层。

### 1.2 核心目标
1. **标准工具中枢**：定义标准的 `AiTool`、`AiToolRegistry`，参数模式严格对齐 MCP 的 `inputSchema`，并提供多协议导出能力（OpenAI Function Calling、Claude Tool Use、MCP Server 导出）。
2. **复用统一查询引擎**：实现 `query_tasks` 工具，底层直接复用 `TaskQueryEngine.filterFlat()`，支持状态、日期、优先级、关键字过滤。
3. **真实元数据感知**：实现 `get_metadata` 工具，向 AI 实时提供系统当前绝对时间戳、星期、项目列表及标签字典，杜绝时间与分类幻觉。
4. **安全写入与修改**：实现 `create_tasks` 与 `update_task` 工具，严格执行“人工确认环路（Human-in-the-Loop）”，生成结构化提案卡片供用户在 UI 审查后确认入库，禁止静默修改。
5. **自主调度中枢（Agent Loop）**：实现 `AiToolRunner`，负责“模型请求 ➔ 工具执行 ➔ 结果注入 ➔ 模型归纳”的多轮自主调度循环。

## 三、 最终实施情况报告 (Implementation Report)

### 3.1 成果落地清单

#### 1. 工具层（Tool Layer）
- **`AiTool` & `AiToolContext`**：
  统一了工具执行的上下文环境（挂载 `TodoRepository` 与当前真实时间戳），工具通过异步 `execute(Map<String, dynamic> arguments, AiToolContext context)` 运行并返回 `AiToolResult`。
- **`AiToolRegistry`**：
  注册了 4 项标准工具，支持一键导出为 OpenAI 格式、Claude 格式，以及 MCP 标准定义（`inputSchema` 遵循 JSON Schema 规范）。

#### 2. 工具实现（Tool Implementations）
- **`GetMetadataTool` (`get_metadata`)**：
  向 AI 注入当前本地时间、格式化日期、星期几，以及系统所有的项目名称、ID、标签名称。解决模型无法得知“今天星期几”、“有哪些现有项目”的问题。
- **`QueryTasksTool` (`query_tasks`)**：
  **核心亮点**：彻底复用 `TaskQueryEngine`。AI 传入参数后，直接映射为 `FilterCriteria`（支持状态筛选、优先级列表、起止日期、关键字），并调用 `TaskQueryEngine.filterFlat()` 执行内存级快速筛选，返回精简的结构化任务列表。
- **`CreateTasksTool` (`create_tasks`)**：
  规范了任务标题、备注、优先级、截止时间与子步骤拆解列表。遵循安全原则，输出带有 `requiresConfirmation: true` 的提案。
- **`UpdateTaskTool` (`update_task`)**：
  支持对已有任务的标题、状态、优先级、截止时间进行修改建议，针对父子任务进行规则校验。

#### 3. AI 客户端与 Agent 调度中枢
- **`AiClient.chatWithTools`**：
  支持 OpenAI 规范（`tools`、`tool_calls`）与 Claude 规范（`tools`、`tool_use`、`tool_result`），自动解析模型返回的工具调用参数。
- **`AiToolRunner`**：
  实现了完整的自主代理循环（Agent Loop）：
  1. 组装系统提示词与可用工具清单；
  2. 发起模型请求；
  3. 若模型返回 `tool_calls`，由 `AiToolRegistry` 自动执行工具并获取数据；
  4. 将工具返回数据打包为 `tool` / `tool_result` 消息送回模型；
  5. 循环迭代直到模型生成最终解答或捕获到任务创建提案。
- **UI 控制器协同**：
  在 `AiCopilotController.sendMessage` 中接入了 `AiToolRunner`。当 AI 发起创建或修改时，UI 端能够无缝唤起既有的任务审查确认卡片。

## 五、 后续演进建议（MCP 外部化支持）

由于本阶段已经在 `AiToolRegistry` 中实现了与 MCP 100% 兼容的 `toMcpDefinitions()` 标准与参数模式，后续若需要对外开放（例如 Cursor、Claude Desktop 或外部脚本接入）：
1. 仅需在 `lib/core/ai/mcp/` 下增加一个极简的 JSON-RPC 2.0 传输层（通过标准输入输出 `stdio` 或本地轻量级 HTTP/SSE 服务）。
2. 将收到的 JSON-RPC `tools/call` 请求直接转发给现有的 `AiToolRegistry.dispatch()` 即可。
3. 无需改动任何底层的数据库、查询引擎或工具逻辑。
