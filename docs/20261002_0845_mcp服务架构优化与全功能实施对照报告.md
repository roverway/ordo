## 1. 实施计划全文

### Phase 1: 基础设施与数据模型（提案暂存与统一执行核心）

#### 任务 1.1: 数据库 `task_proposals` 暂存表设计与迁移
- **目标**：在不破坏主业务数据库 schema 稳定性的前提下，创建持久化提案暂存表。
- **表结构**：
  - `id`: TEXT PRIMARY KEY
  - `type`: TEXT NOT NULL (`create` / `update` / `delete` / `bulk_create`)
  - `status`: TEXT NOT NULL (`pending` / `confirmed` / `rejected` / `expired`)
  - `payload`: TEXT NOT NULL (JSON 数据内容)
  - `idempotency_key`: TEXT NULL (支持客户端重试幂等)
  - `error_message`: TEXT NULL (执行失败时的诊断信息)
  - `created_at`: INTEGER NOT NULL (UTC 毫秒)
  - `expires_at`: INTEGER NOT NULL (默认 7 天过期)
  - `applied_at`: INTEGER NULL (确认落库时间戳)
- **索引**：`idx_task_proposals_status`、`idx_task_proposals_idempotency`、`idx_task_proposals_created_at`。

#### 任务 1.2: 提案仓储层 `ProposalRepository`
- **目标**：封装提案的生命周期操作，作为审查模式（Review Queue）的核心支撑。
- **核心接口**：
  - `createProposal({required type, required payload, idempotencyKey, ttl})`
  - `confirmProposal(String id, TodoRepository repository)`：事务内应用提案并落库
  - `rejectProposal(String id, {String? reason})`：废除提案
  - `listProposals({String? status, int limit, int offset})`
  - `cleanExpiredProposals()`

#### 任务 1.3: 统一任务写入执行器 `AiTaskExecutor`
- **目标**：遵循单一权威内核原则，将直接写入（Direct Write）、提案确认（Proposal Confirm）以及批量创建（Bulk Create）的写入逻辑统一封装为 `AiTaskExecutor`。
- **能力**：
  - 项目合法性校验（自动 fallback 至 `inbox`）
  - 任务主记录持久化
  - 子任务层级树（`substeps` / `children`）创建与绑定
  - 标签解析与跨表关联（不存在的标签自动以设计蓝建立）
  - 属性解析（优先级、截止时间、开始时间、描述）

### Phase 2: 安全鉴权与服务端网关增强（HTTP / API Key）

#### 任务 2.1: API Key 存储与配置持久化
- **目标**：在 `AiConfigService` 中管理安全凭据与服务端运行参数。
- **配置项**：
  - `isMcpAuthEnabled`: 是否要求外部客户端鉴权（默认 true）
  - `mcpApiKey`: 自动初始化生成的安全令牌（格式 `ordo_sk_<uuid>`）
  - `mcpWriteMode`: 写入模式策略（`direct` 直接写入 vs `review` 提案队列）
  - `regenerateMcpApiKey()`: 重新生成并使旧密钥失效

#### 任务 2.2: `McpServer` 网关安全中间件
- **目标**：阻止未经授权的外部调用，并在协议层拦截非本机非法访问。
- **实现规则**：
  - 严格绑定 `127.0.0.1`，外部公网无法访问。
  - CORS 守卫：限制仅允许 `localhost` / `127.0.0.1` 来源，外部 Origin 拦截 `403 Forbidden`。
  - 标头支持：双通道支持 `x-api-key: <token>` 以及 `Authorization: Bearer <token>`。
  - 鉴权拦截：若未携带或密钥不匹配，返回 HTTP 401 及 JSON-RPC 错误码 `-32001 (Unauthorized)`。

#### 任务 2.3: 协议健壮性与结构化错误信封
- **目标**：杜绝网络悬挂，提供 LLM-first 的机器可读错误提示。
- **防护措施**：
  - 接入 10 秒超时（`timeout(Duration(seconds: 10))`）读取请求体，防恶意悬挂。
  - 错误信封格式：
    ```json
    {
      "ok": false,
      "errorCode": "PROJECT_NOT_FOUND",
      "error": "指定的项目不存在: invalid-proj",
      "errorHint": "请先调用 get_metadata 获取可用项目列表及有效 projectId",
      "errorDetails": { "invalidProjectId": "invalid-proj" }
    }
    ```

### Phase 3: 提案闭环与批量能力工具开发（11-Tool Suite）

#### 任务 3.1: `create_tasks` 写入工具升级为双轨模式
- 支持参数：`title`（必填）、`projectId`、`description`、`priority`、`dueDate`、`startDate`、`tags`、`substeps`、`mode`、`idempotencyKey`。
- 模式判断：
  - `mode: 'direct'` 或当前全局为 direct 模式：直接由 `AiTaskExecutor` 写入主数据库，返回 `status: "created"`、真实 `taskId`、`requiresConfirmation: false`。
  - `mode: 'proposal'` 或当前全局为 review 模式：写入 `task_proposals`，返回 `status: "pending"`、`proposalId`、`requiresConfirmation: true`。

#### 任务 3.2: `update_task` 升级为双轨模式
- 支持对已有任务修改：`title`、`description`、`status`、`priority`、`dueDate`、`clearDueDate`、`projectId`、`tags`。
- 校验目标任务必须存在；同样支持直接更新与提案暂存。

#### 任务 3.3: 批量创建工具 `create_tasks_bulk`
- 支持单次最多 100 个任务批量传入；
- 支持 `dryRun: true` 预检模式：仅执行参数校验和推演，不执行落库，返回校验通过/失败清单与修复指引；
- 非原子独立写入：成功与失败明细清晰返回，单项失败不阻断整体流程。

#### 任务 3.4: 提案闭环管理工具（3 个）
- `list_proposals`：查询提案队列，支持状态过滤（`status: pending/confirmed/rejected`）与分页。
- `confirm_proposals`：批量提交提案，逐一应用到 SQLite，返回对应的 `taskId`。
- `reject_proposals`：批量作废提案。

#### 任务 3.5: 深度单任务详情工具 `get_task`
- 根据 `taskId` 返回完整任务结构：包括项目名称（`projectName`）、递归子任务树（`subtasks`）、关联标签（`tags`）与完整描述。

#### 任务 3.6: 批量任务删除工具 `delete_tasks`
- 支持传入 `taskIds` 数组批量硬删除/级联删除；支持直接删除与提案暂存模式。

#### 任务 3.7: 统计聚合分析工具 `aggregate_tasks`
- 高效 SQL 原生聚合：按状态（`status`）、优先级（`priority`）、项目（`project`）或标签（`tag`）分组统计数量，避免客户端全量读取数百条任务造成 LLM 上下文溢出。

#### 任务 3.8: 现有查询工具 `query_tasks` 增强
- 新增 `fields` 字段投影能力（例如只拉取 `['id', 'title', 'status']`）；
- 新增 `projectId`、`projectName`、`tagIds` 结构化多维过滤；
- 新增基于游标的 `cursor` / `limit` 分页控制。
