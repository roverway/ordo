## 序言：重识任务管理的本质

当大多数人做 AI 助手时，他们只是把一个千篇一律的聊天框塞进软件侧边栏。他们以为只要接入了大语言模型，软件就拥有了灵魂。

**他们完全错了。**

一个真正专注于任务管理的 AI 助手，绝不是一个陪用户天南海北聊天的聊天机器人，也不是一个只会在输入框里吐出一堆冰冷文字的打字机。

在 Ordo 中，AI 应当是用户的**外脑与幕僚长（Chief of Staff）**：
1. **它拥有透视眼**：对系统里的任务脉络、时间切片、完成轨迹了如指掌；
2. **它尊重人的意志**：它提议，由人裁决；所有的输出都应该是**可触摸、可编辑、可直接行动**的，而不是不可交互的文本废话；
3. **它拥有持久连贯的思考**：它记住每一次上下文推演，明白“把它拆细一点”里的“它”究竟代表什么；
4. **它克制而优雅**：买一瓶牛奶不需要被拆解成“穿鞋、出门、付款”三部曲；而一个真正宏大的发布会，它会提供恰到好处的战术拆解。

基于这一哲学，我们对前一阶段的 AI 助手实现进行了彻底的解剖与重塑。

## 第一部分：全景问题诊断与根因解剖

### 缺陷一：统一搜索后端的“时间失明症”
* **现象**：询问 AI 助手“我昨天完成了什么”、“上周我的主要产出是什么”时，AI 助手要么胡言乱语，要么回复“没有找到相关任务”。
* **根因深度解剖**：
  1. **元数据在传输端被阉割**：在 `QueryTasksTool` 的序列化层中，只输出了 `id`、`title`、`status`、`priority` 与 `dueAt`，核心的时间戳 `completedAt` 与 `createdAt` 完全缺失；
  2. **父子任务派生规则断层**：Ordo 拥有严谨的任务树哲学——当一个复合任务的所有子任务都完成时，父任务状态应当为 `done`，而父任务自身的完成时间应当取其子树中最新完成的时间（即 `derivedCompletedAt`）。原有的后端检索直接取底层数据库中的单字段，导致拥有子任务的父任务完成时间始终为空；
  3. **缺乏时间范围检索协议**：模型无法用语义化的方式（如 `today`、`yesterday`、`lastWeek`）要求引擎检索特定时间段完成的记录。

### 缺陷二：Markdown 渲染引擎的“退化断层”
* **现象**：明明在待办详情和长文本中已经研发了强大的 AST Markdown 渲染引擎，但在 AI 助手对话流中，排版一片混乱，列表、粗体、代码块全部退化成了粗糙的生文本。
* **根因深度解剖**：
  1. 在 `AiCopilotSheet` 的消息渲染流中，助手文本被简单地用了一个死板的 `Text(msg.content)` 渲染；
  2. 气泡的最大宽度被硬编码限制在 `280px`，使得大模型返回的结构化对比、复盘要点挤压在狭窄空间内，完全丧失了设计呼吸感。

### 缺陷三：连续对话的“金鱼记忆”
* **现象**：用户说“明天上午准备项目复盘”，AI 输出了提案；用户接着说“帮我把这个会议细化拆解一下”，AI 却茫然反问“您想拆解哪一个任务？”。
* **根因深度解剖**：
  1. `AiToolRunner` 的 Agent 循环此前是完全无状态的单轮运行，入参仅有 `userPrompt`；
  2. 状态控制器 `AiCopilotController` 没有维护送入大模型的上下文历史，导致每次网络请求都从零开始。

### 缺陷四：任务分解与卡片交互的“契约崩塌”
* **现象**：
  - 用户明确要求“把方案拆解成可执行步骤”，大模型却直接在聊天文本中生成了 1、2、3 文本列表，而**不弹出**可供用户勾选、修改或一键添加入库的卡片；
  - 或者用户仅仅说“买瓶酱油”，大模型却自作聪明地拆解出“去超市”、“结账”等毫无意义的碎片。
* **根因深度解剖**：
  1. **系统提示词缺乏强制契约**：大模型没有被告知“创建与分解任务**必须且只能**调用 `create_tasks` 工具出卡片，严禁在正文中用纯文本假装完成分解”；
  2. **缺乏原子任务与复合任务的判定准则**：未定义单一行动与复合目标的清晰界限；
  3. **缺少防御性兜底架构**：当模型偶尔因为随机性返回了文本列表时，系统没有自动识别并纠正为提案卡片的容错机制。

### 演进要点一：动静分离与卡片优先（Card-First Principle）
* **原则**：AI 绝不在聊天框里自说自话地把任务直接写死进数据库，但也绝不只给一串死气沉沉的文本。
* **实现**：AI 调用 `create_tasks` 工具，中断 Agent 循环，渲染出拥有 Linear 极简质感的 `AiTaskProposalCard`。用户可以在卡片上行内编辑标题、点击徽标循环切换 P0-P3 优先级、选择或剔除个别子步骤，最后由人按下“添加到待办”。

### 演进要点二：时空感知与派生状态（Derived Temporal Perception）
* **原则**：任务的真实完成时间不仅存在于单张任务表，更体现在任务树的动态收敛中。
* **实现**：后端查询引入 `derivedStatus` 和 `derivedCompletedAt`。结合 `completedScope`（'today' | 'yesterday' | 'thisWeek' | 'lastWeek'），大模型在被问及过去表现时，能精确调取历史数据，输出具备高管洞察力的高质量复盘。

### 演进要点三：连续认知流（Continuous Cognitive Flow）
* **原则**：对话不应是一次性的命令响应，而是一场思想的共创。
* **实现**：10 轮滑动窗口上下文。不仅仅保留文本对话，还将历史中出现的任务方案（如《产品发布会》含 3 个步骤）压缩成语义摘要回传给大模型。用户可以使用代词，层层推进待办规划。

| :--- | :---: | :--- |
| `lib/core/ai/tools/impl/query_tasks_tool.dart` | 重构增强 | 引入 `derivedCompletedAt` 与 `derivedStatus` 处理任务树递归状态；扩展 `completedScope`（'today', 'yesterday', 'thisWeek', 'lastWeek', 'customRange'）与绝对时间戳过滤；输出补齐 `completedDate`, `completedAt`, `createdDate`, `createdAt`, `description`, `subtaskCount`, `completedSubtaskCount`。 |

本次重构落地了完备的双层测试金字塔（底层 Tool/Runner 单元测试 + 上层 Sheet/Controller Widget 测试），所有用例均一次性通过：


#### 覆盖的核心测试集：
1. **`test/core/ai/tools/ai_tools_test.dart`**：
   - 验证了 `QueryTasksTool` 对昨天完成任务的 `completedScope: 'yesterday'` 过滤；
   - 验证了包含子任务的复合父任务在全部子任务完成时，`QueryTasksTool` 成功输出派生后的完成时间 `derivedCompletedAt`、子任务总数及已完成子任务数。
2. **`test/core/ai/tools/ai_tool_runner_test.dart`**：
   - 验证了 `AiToolRunner` Agent Loop 在处理多轮对话时，严格将 `history` 消息队列按时序编织在系统提示词与当前提问之间。
3. **`test/features/ai_copilot/ai_copilot_sheet_test.dart`**：
   - 验证了 AI 助手文本消息在界面上使用了自研的 `MarkdownContentView` 组件进行渲染，标题与粗体文本排版完全符合预期；
   - 验证了从输入、发送、审查卡片、勾选子步骤到持久化入库的全流程。
4. **`test/features/ai_copilot/ai_copilot_controller_test.dart`**：
   - 验证了状态机的多轮交互流转、卡片字段实时行内编辑与入库事务隔离。

### 三、 成果体验与交互细节对比

| 体验维度 | 改造前 | 改造后（当前实现） |
| :--- | :--- | :--- |
| **完成情况问答** | 模型表示“未查到相关任务”或仅凭幻觉编造 | 精确回答“昨天共完成了 2 个任务，其中《演讲稿准备》耗时 2 天完成，包含全部 2 个子步骤推进完毕” |
| **排版质感** | 挤在 280px 的生硬纯文本，无法解析 Markdown | 宽阔呼吸感、精美自研 AST Markdown 渲染，加粗、列表、标题层级分明 |
| **连续对话** | 单轮遗忘，每句话都像第一次对话 | 拥有 10 轮时空记忆，轻松理解“把它拆细一点”、“把第三个子步骤去掉”等连续指代 |
| **任务创建与分解** | 口头在文本中列出步骤清单，无法一键加入待办 | 铁律约束调起交互卡片，支持行内轻点编辑、按需勾选子步骤，一键添加到待办数据库 |

Ordo AI 助手已经脱胎换骨。它不再是一个笨拙的对话框，而是一个懂时间、懂结构、懂克制的高效能伙伴。
